# Greeting rebuild — first-timer vs returning customer

Jason, 2026-09-05. Queued behind the in-flight chat-sms defect work (same file).

## FIRST-TIME customer — two messages, not one wall

**Message 1**, three parts:

1. Warm welcome + the shop's personality line.
2. What they can do + the fee:
   "You can order right here and pay by text when you're done — we're pickup only
   at the moment. Heads up: there's a $0.99 service fee per order, so nothing
   surprises you at checkout."
3. Compliance, smaller/italic voice:
   "Msg & data rates may apply. Reply HELP for help, or STOP and we'll never text
   you again 😔"

**Message 2**, sent separately: "What can I get you today?"

## RETURNING customer — the ENTIRE greeting

    Hey Jennifer! What can I get you??

No compliance block. No fee restatement. No welcome-back paragraph. A regular
gets treated like a regular.

- **Keep the double question mark.** Deliberate casual voice. Do not "correct" it.
- Phone match but no name → `Hey! What can I get you??`
- **Never** invent a name. **Never** render "Hey null".

## Constraints

**A — Compliance wording (verified against the live registration, not the code comment).**
Campaign CSMB9HG is ACTIVE; its registered flow says consumers receive HELP + STOP +
the rates disclosure "on first contact". Jason's wording keeps all three elements, so
no re-registration is required. The keyword auto-responses (`helpMessage`,
`optoutMessage`, `optinMessage`) are separate registered strings — DO NOT TOUCH THEM.
HELP and STOP must keep working on every message regardless of greeting variant.

**B — Delivery clause must be true.** Source it from the shop's EFFECTIVE delivery
capability (the same condition the ordering engine uses to accept a delivery order),
never the raw `delivery_enabled` flag. Vito's has `delivery_enabled = true` with no
radius, so the flag says delivery while the engine refuses it. The greeting must never
promise what the engine will refuse.

**C — Personality line is per-shop data, never hardcoded.** New `tagline` column on
`shops` (owner-editable; belongs in the Menu & Settings editor). `shop_context` is NOT
a substitute — it is a scraped research paragraph (Not Just Bagels' is ~1,900 chars).
If a shop has no tagline, OMIT the line. Never invent one.

**D — Fee restatement removed** (paired with the Test Kitchen defect work): running
item count and total every turn; the subtotal + service fee breakdown once when it
first applies, and again at checkout. Disclosure before payment is preserved.

## Recognition — scope is recognition + greeting ONLY

Closes CRM backlog 302edb08. Do NOT build order history, reorder, or "the regular".

- There is no customers table. The name is the most recent
  `order_carts.pickup_name` reached via `conversations.customer_phone`.
- **Scope the lookup to the shop.** Tenant isolation is absolute — a customer who gave
  their name to one restaurant must never be greeted by name by another.
- A pickup name is whoever collects the food, not necessarily the texter. Recognition
  is best-effort: no confident name → the generic warm variant, never a wrong name.
- **Web/Test Kitchen degrades to first-timer by construction**: the web path uses
  `web:<session_id>`, unique per session, so the lookup can only return nothing. Prove
  it with an explicit test rather than relying on the accident.

## Open, deliberately not blocking

Whether opt-out language must appear on every message for consumer-initiated
conversational traffic, or once per conversation, is genuinely ambiguous — our own
`docs/10dlc-compliance-obligations.md` says both: line 107 says "first message to a
consumer number **in a conversation**", line 178 says "first reply to a **new
number**". Asked Telnyx support 2026-09-05. Ship Jason's version now; if Telnyx says
otherwise, add a compact `Reply STOP to opt out.` to the returning greeting — a
one-line change, deliberately isolated so it stays one line.

## Acceptance

2. Returning customer with a known name gets exactly `Hey <Name>! What can I get you??`
   — double question mark intact, nothing else appended.

## E — Name prompt: ONE wording, both order types (Jason, 2026-09-05 12:59 ET)

Supersedes the pickup/delivery branching asked for at 12:51 — Jason overruled it.
No conditional. Customer-facing wording only; `pickup_name` keeps its name.

    What's your name for the order?

**SHIPPED** ahead of the rest of this spec — it is independent of the greeting
rebuild and two of the sites were wrong today. Single source of truth:
`NAME_ASK` in `chat-sms/index.ts`, used at all four code sites, so nobody can add
a fifth divergent string. The two prompt rules (MONEY/SCOPE + checkout rule)
instruct the exact wording for pickup AND delivery alike.

Sites changed: 1475/1480 driver-tip shortcut, 1732 ledger status, 4382 Guard 2,
plus prompt lines 624/629.

**The driver-tip lines were a live bug.** A driver tip only exists on a delivery
order, so both said "pickup" on a path that is delivery by construction.

### C2 detector — fixed in the same commit (index.ts:3971)

The pre-LLM name→submit shortcut decides the bot asked for a name by regex-matching
the previous assistant message. "What's your name for the order?" matched none of
its alternatives, so shipping the copy alone would have silently dropped every
order out of C2 and back onto the LLM for the name turn — the exact hallucination
path C2 exists to prevent. Added `(?:for|on) (?:the|this|your) order`; verified all
four rendered asks now match and an unrelated question still does not.

Prose-sniffing remains fragile: a deterministic "asked for name" flag on the cart
is the right fix and stays queued, not shipped.

### Apostrophe

Straight `'`, deliberately. U+2019 is not in GSM-7 and would push every SMS
containing it to UCS-2 — 67 chars per segment instead of 153, on a message the
customer sees in every single order.

### Returning-greeting fallback stays

`pickup_name` is a hard gate on `submit_order`, so every *completed* order has a
name. The no-name fallback (`Hey! What can I get you??`) still ships: it covers
someone who texted before but never completed an order — a real share of second
visits.
