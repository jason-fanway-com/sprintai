## 4. In flight right now — the lexicon fix

**Jason approved this at ~04:05 and the crew is building it.** Dispatch:
`00-L-lexicon-variants-spec`.

The defect: Vito's lexicon has `cheese burger` ($8.49) and `bacon cheeseburger` ($10.99) but **no
single-word `cheeseburger`**, so the only term containing that token points at the dearer item.
`propose.ts` resolved a plain "cheeseburger" to the $10.99 row on **11 of 17** live calls.
Injecting the real lexicon made it *worse*, which is what proved the gap was data, not code.

The fix: `compile-menu` emits **space-collapsed and plural** surface-form variants, each kept only
when it resolves uniquely. Measured by me across all three real shops before speccing:

```
space-collapsed:  Vito's 287 / Zio's 501 / NJB 218  = 1,006 new terms, ZERO collisions
plural:           Vito's 303 / Zio's 557 / NJB 254  — 3 collisions, all naive-plural junk
                  ('meatballses'); rule: do not pluralise a term already ending in 's'
```

**Acceptance (do not relax it):** unit tests; recompile **Vito's only** first and prove
`cheeseburger` → `442f650d` by querying `lexicon`; then re-run the six-phrasing matrix asserting
**the resolved item and price**, not schema validity; Zio's and NJB only after you read that.
Purely additive — if a recompile would change or remove an existing term, stop. No menu is
re-imported, least of all NJB's hand-corrected one.

Jason's direction behind it, now in PO-BRIEF §4c: *"solving those kind of problems with data in
anticipation of real user behavior."* Generate the surface forms people type; never a runtime
matcher.
