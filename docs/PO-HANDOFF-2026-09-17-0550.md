## 6b. The permission gap — fix this before relying on an Air-hosted PO thread

Jason travels and wants the PO thread to live on the Air, driven from the desktop app and
from his iPhone, so work continues when his laptop is shut. Two separate problems block that.
Neither is hypothetical — both happened on 2026-09-16.

**Problem 1: an Air-hosted session had narrower permissions than the laptop session and
could not do the job.** It could read the repo and download the deployed artifact, but it was
refused:

- writing a `.msg` into `~/.openclaw-sprintai/po-outbox/` — so it could not dispatch anything
- any direct PostgREST read — so it could not check a cart, a lexicon or a flag
- `turn-engine-flag.sh`, even on its read-only `status` path

The result was a PO that could verify work but not act on it. It sat unable to dispatch a
deploy while the laptop session did it instead. That is not a remote PO, it is a spectator,
and it silently moved the real work back onto the machine that travels.

**Before trusting an Air-hosted thread, have it prove all three:**

```bash
# 1. can it dispatch?
scp /tmp/probe.msg openclaw-air:'~/.openclaw-sprintai/po-outbox/00-ZZ-probe.msg'
# 2. can it read state?
curl -s "$SPRINTAI_CHAT_SUPABASE_URL/rest/v1/shops?select=id&limit=1" \
     -H "apikey: $SPRINTAI_CHAT_SUPABASE_SERVICE_ROLE_KEY" \
     -H "Authorization: Bearer $SPRINTAI_CHAT_SUPABASE_SERVICE_ROLE_KEY"
# 3. can it read the flag?
/Users/joestrazza/po-scratch/turn-engine-flag.sh status
```

If any is refused, fix the profile until all three pass. Do not work around it by asking
another session to act on its behalf — that is permission laundering and it is explicitly
refused elsewhere in this project. Route it to Jason instead.

**Problem 2, and this is the one Jason cares about most: he cannot interact with the Air's
Claude threads from the desktop app on his laptop.** A session on another machine is visible
to *other Claude sessions* as a Remote Control peer — they can message it — but that is not
the same as Jason being able to open it, read it and type into it from the app he actually
works in. Until that is solved he is relying on a relay: he talks to the laptop session,
which messages the Air session. That relay dies the moment his laptop closes, which is
precisely the situation the setup exists to survive.

Whoever picks this up should establish, concretely and by testing rather than assuming:
which surfaces can attach to an Air-hosted session (desktop app sidebar, claude.ai on the
web, the iPhone app), what has to be enabled on the Air session for each, and whether a
session started on the Air appears in Jason's own session list at all. Report what actually
works, not what should.
