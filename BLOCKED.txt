2026-09-08 ~15:25 UTC — REAL ROOT CAUSE FOUND: the compiled engine cannot
resolve "pepp" (or any abbreviation) to a real choice AT ALL — this is why
the live battery's RUN 1 reproduced the exact pre-D1-fix merge shape despite
the fix being deployed, and it is the same event driving the 135-137s number
================================================================================

Confirmed empirically (not inferred) by running the actual deployed
functions directly against the literal test wording:

  matchChoiceInText(choices=[Pepperoni,...], "...1 pepp, 1 plain...") -> null
  matchChoiceInText(choices=[Pepperoni,...], "...1 pepperoni, 1 plain...") -> MATCHES "Pepperoni"

significantStems/stemWord (pending-disambiguation.ts) only strips a
trailing plural — "pepp" stems to "pepp", "Pepperoni" stems to "pepperoni".
These are different strings; matchChoiceInText's `allPresent` check requires
literal stem presence, so the reactive text-matcher NEVER resolves an
abbreviation to a real choice, full stop. This is true with or without this
morning's consumedModifierChoiceIds fix — that fix only prevents an ALREADY-
matched choice from being re-matched by a second call; it does nothing when
NEITHER call ever matches anything, which is exactly what happens on every
"pepp" (not "pepperoni") run.

Confirmed by code read: executeTool's compiled add_item branch (index.ts,
~954-963) calls applyCompiledAddItem with `compiledMatchText ?? customerMessage`
only — the tool call's own `modifiers`/`options` input (what the LLM itself
tried to pass, e.g. having correctly reasoned "pepp" -> Pepperoni per the
"COMPOSING A TOPPING-ONLY PIZZA REQUEST" system prompt rule) is destructured
and then NEVER READ for a compiled item. There is no code path for the
model's own composed intent to reach ask_plan_selections. The model's only
way to force a modifier onto a compiled line is to separately call
modify_item afterward — which is a FULLY legacy, ask_plan-unaware handler
(confirmed: zero occurrences of ask_plan/compiledEngineEnabled/applyCompiled
inside the modify_item case) that will happily accept and directly apply an
explicit `options` param, writing straight to `options`/`price_cents` and
bypassing ask_plan_selections and consumedModifierChoiceIds entirely.

This explains EVERY observed shape across the different test runs, not just
one:
  - quantity:2, modifiers:[] (BLOCKED.txt RUN 1 above, session A3E587A0):
    neither add_item call for "1 pepp"/"1 plain" ever resolves a topping
    (matchChoiceInText returns null both times) -> both compute IDENTICAL
    topping-less selections -> applyCompiledAddItem's identicalExisting
    dedup correctly (given wrong inputs) merges them to quantity:2. This is
    the DEFAULT outcome for the literal acceptance-test wording, with or
    without the D1 fix.
  - 4 correct lines, Pepperoni split cleanly (order_carts 32b71e14,
    d3541dd7): only explainable if the model ALSO called modify_item
    separately to force the option in — a side-channel the design never
    accounts for, not the intended compose mechanism, and not exercised by
    any existing test.
  - 3 lines, one plain cheese pizza with zero options at all (order_carts
    cf233aae, b4d9d44d, the 137s/135s runs): the model attempted the compose
    for "1 plain" but never issued a 4th call representing "1 pepperoni" at
    all — consistent with the model being unable to make its own "pepp"
    resolution stick via add_item and giving up rather than reaching for
    modify_item. The shortfall-retry backstop (enumeration-shortfall-retry.ts)
    correctly detected the count mismatch and retried up to its 2-attempt
    budget — each retry a full extra round trip carrying the ~28K-token
    system prompt — before falling through to the honest-decline fallback.
    THIS retry-and-fail loop is the dominant cost inside the 135-137s figure.

Root cause is one sentence: the compiled engine was designed to accept a
modifier selection ONLY via reactive text-matching against real choice
display names (spec P1, "the model phrases, code decides" — deliberate,
per ask-plan-engine.ts's header), but nothing lets the model's own resolved
intent (informed by system-prompt rules like the pepp-compose instruction)
reach the engine directly, and the reactive matcher has no tolerance for
any wording that doesn't literally contain a real choice's stem.

NOT FIXED — flagging fix direction, not implementing without sign-off, since
this changes applyCompiledAddItem's core contract for every compiled shop:
  (a) Let executeTool's compiled add_item branch also honor the tool call's
      own `options`/`modifiers` input when it names a REAL compiled choice
      (validated against askPlan.steps, same validation discipline legacy
      add_item already applies against option_groups) — model-asserted
      selections take priority, matchChoiceInText stays as a backstop for
      whatever the model didn't explicitly pass. Symmetric with how legacy
      add_item already works; most direct fix for the actual gap.
  (b) Broaden matchChoiceInText to tolerate common abbreviations/prefixes —
      rejected as a first choice: real false-positive risk on a menu the
      size of Zio's (494 groups/3449+ choices) where a short abbreviation
      could prefix-match more than one real choice.
  (c) Make modify_item compiled-engine-aware (route through
      ask_plan_selections/consumedModifierChoiceIds like add_item does) —
      fixes the state-consistency half of this independently of (a)/(b),
      worth doing regardless of which direction is chosen for the primary
      gap, since a model that reaches for modify_item on a compiled line
      today silently desyncs authoritative state either way.
Awaiting direction before implementing any of the above.
